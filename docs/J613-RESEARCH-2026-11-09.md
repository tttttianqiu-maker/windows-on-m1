# J613 research sweep, 2026-11-09

What was checked, what it means for this project, and the next experiment for
each open item. Sources at the end. Rules from `AGENTS.md` apply: one variable
per hardware run, ledger before and after.

## 1. SErrors: TrustZone carveouts were mapped (fixed, build 38+)

- m1n1's `mcc_init()` had no `mcc,t8122` case, so `mcc_unmap_carveouts()` did
  nothing on the M3: the TZ carveouts stayed mapped as normal memory for m1n1
  (EL2) and in the guest's stage 2 (proxyclient `unmap_carveouts()` got an
  empty list).
- Upstream m1n1 added T8122 MCC support on 2026-08-07 (Janne Grunau,
  `fddbddf8`, "mcc: Add support for T8122 SLC and carveouts"), after this fork
  split off. The unmap exists because, in Hector Martin's words (`50a95930`),
  "This is necessary to stop the guest from speculating into carveouts."
- m1n1 issue #97 shows the same signature on an M1: `ESR 0xbe000000`,
  `L2C_ERR_ADR 0x300000bd9498000` (low 42 bits = the faulting PA) when memory
  past usable RAM is touched. Our two addresses decode to 0x103fbbdc140 and
  0x103fc1f4600, 64-68 MiB below the top of the 16 GiB DRAM.
- Fix: m1n1 `90dbf4c` (T8122 TZ registers stride 0x14, start 0x6cc, end 0x6d0,
  enable 0x6d8, as upstream). Diagnostics: the SError dump says whether
  L2C_ERR_ADR is in a TZ carveout (`90dbf4c`) or above usable RAM (`9b43b36`).
- If SErrors persist with the MTP **on**: Aurora's J613 u-boot keeps the MTP
  OSLog buffer in the helper's own SRAM ("Older MTP firmware retains OSLog in
  SRAM", top of SRAM, 16 KiB aligned) and calls a DRAM OSLog "unsafe"; it also
  notes "Firmware keeps OSLog even after QUIESCED and ASC RUN is cleared".
  Ours is in m1n1's heap behind the MTP DART (translation, not bypass), so a
  stray write cannot leave that buffer. Moving it to SRAM is the next variable
  only if SErrors return with the MTP on.
- The logged OSLog request `0x0106000000000000` asks for 0x6000 bytes; we
  allocate 32 KiB, so "buffer too small" is ruled out.

## 2. Windows Setup failures

- The prep never staged `oobe-unattend.xml` on WINSRC; WinPE now refuses to
  format without it (`73a0cab`), the prep downloads it (`461348a`), and
  `--no-driver` keeps the AppleMtpInput driver and test signing out of a
  reinstall. The last reinstall changed two things at once (reinstall plus a
  never-loaded driver).
- `oobe-unattend.xml` no longer forces `UILanguage en-US` (harmless on an en-US
  image, risky on English International).
- "Windows could not complete the installation" / "restarted unexpectedly"
  are what a hard reset in the middle of specialize/OOBE produces; the
  ChildCompletion `setup.exe=3` resume (`--fix-setup`) is the standard fix,
  a reinstall is the reliable one.
- Watcher follow mode already restarts the run after every guest-requested
  reboot ("PSCI RESET" in hv-tail.log), so WinPE -> Setup -> desktop needs no
  manual step unless m1n1 crashes.

## 3. Display on the Air itself (build 39+, `j613 screen on`)

- The M3 DCP firmware rejects a new guest surface (`0xe00002c2`,
  EXP-20261105-006). Linux on J613 without a DCP handoff "falls back to
  simpledrm", i.e. iBoot's boot framebuffer stays scanned out.
- m1n1's `hv.start()` only calls `fb_shutdown(True)` (stops m1n1's console),
  the DCP keeps showing the boot surface. New `hv_fb_mirror` copies the guest's
  virtual framebuffer into it a few rows per hv tick (x2r10g10b10 conversion),
  ~12 fps at 4 rows/tick (`J613_SCREEN_ROWS` tunes it).
- Aurora has a full J613 DCP mapping handoff (m1n1-aurora
  `kboot_display_handoff.c`, profile `dcp_soc_j613_25g83`, stub firmware
  macOS 26.6.2 "25G83" only). Brightness and real modesetting need that path
  plus a Windows display driver; not attempted.

## 4. USB in Windows: root cause understood

- Linux `drivers/usb/dwc3/dwc3-apple.c` documents the behaviour seen in
  EXP-20261107-029..037 almost word for word: "After both the PHY and dwc3 are
  initialized we will only ever see a single 'new device connected' event ...
  XHCI's port status register actually does show the correct state but no
  interrupt ever comes in." Cause: the USB2 D+/D- lines go through an eUSB2
  repeater that the TPS6598x-family USB-PD chip resets out of band on every CC
  (dis)connect, which needs a PHY reset to resynchronise. Linux keeps
  everything off until a cable event, then brings up PHY -> DWC3 -> PIPE ->
  xHCI, and tears it all down on disconnect. Wrong orders lead to a broken
  port or "some watchdog kicks in after a few seconds and forces a full SoC
  reset".
- Mu consumes the one event; Windows' inbox xHCI driver never gets another.
- EXP-20261107-032's USB2 PHY power cycle reset the Air because it ran with
  the DWC3 up; Linux first holds the DWC3 in reset with clamps on via the
  pipehandler `AON_GEN` register (`atcphy_dwc3_reset_assert`).
- Latest log (run 20261108-133624) shows `P1=0x2202a0` (CSC + PRC set, CCS 0)
  where EXP-029..036 always saw `0x2a0`: with the EXP-037 DART re-prep the OS
  now sees the connect and resets the port, then the device drops and no
  interrupt arrives (`IMAN0=0x3`, `USBSTS=0x18`, irqs=0).
- Next experiments (build 40):
  1. passive: the trace now prints `HV: xHCI AIC 1030 hw_level=.. masked=..`
     (raw AIC input level) to tell "DWC3 never raises the IRQ" from "masked or
     not delivered";
  2. `j613 usb reset`: at Windows' xHCI reset m1n1 runs the Linux-ordered
     sequence (DWC3 reset + clamp, USB2 PHY off/on, host mode, release, Mu's
     DWC3 core init). Off by default; do it with a stick plugged in before
     boot, after Windows is stable. Failure mode to expect: an Air reset.
  3. Hot-plug needs m1n1 to watch hpm1 `int_event` for CC changes and redo
     the sequence; Windows' xHCI must then be made to reset (e.g. report a
     host controller error through the xHCI trap). Design only.

## 5. Booting without the Hackintosh

- Truly native Windows is blocked by the interrupt controller: the Windows
  HAL needs a GIC, the AIC is not one, and the interrupt-controller
  HAL-extension route "was removed before Windows 8 RTM" (xorica27). NT for
  ASi lists its AIC HAL extension as "needs more work"; Aurora's Mu has a
  `feat/native-aic-acpi` branch (AIC3 CSRT + GIC-free MADT) as groundwork
  only. Every project that reaches a Windows desktop keeps an EL2 shim.
- So "standalone" = m1n1's autonomous mode on the Air. It exists, but the
  runtime is J313-only (`J313_AUTONOMOUS_LAYOUT`, `hv_launch_golden_j313`,
  `HV_J313_STANDALONE_CONTRACT_SCHEMA`); on J613 it stops at
  `PREFLIGHT FAIL checkpoint=PRE_HV_INIT field=11` = `BOOT_RAM_SIZE`.
- Plan: a J613 layout/golden/schema (from `config/j613-guest-layout.json`),
  then port every assisted-mode step `run_uefi.py` does from the host (ADT
  edits, stage-2 tracers, PCI ECAM, xHCI hook, vUART, framebuffer, MTP
  firmware, carveout unmap) into the C runtime, then the ESP install of that
  image. Several hardware rounds; start only once the assisted path is stable.

## 6. Other wishlist items

| Item | Status / path |
|---|---|
| Battery | Feasible: ACPI Control Method Battery (PNP0C0A, `_BIX`/`_BST`) in the DSDT reading an m1n1-backed OperationRegion (like AVHD) that m1n1 fills from SMC battery keys. Needs a Mu (DSDT) rebuild and periodic SMC reads in m1n1. |
| Sleep | Not realistic under the hypervisor (Windows on ARM uses Modern Standby, needs a PEP); sleep/hibernate are disabled by postcfg on purpose. |
| Wi-Fi / Bluetooth | Apple's Broadcom combo chip sits on PCIe behind m1n1 with Apple firmware; no Windows ARM64 driver exists. Realistic: a USB Wi-Fi/BT dongle once USB works. |
| Audio | Speakers need the TAS27xx amps + MCA/ADMAC + speaker safety; no Windows driver. Realistic: USB audio once USB works. |
| Webcam | ISP firmware + driver; Linux only. No path for Windows now. |
| GPU | No Windows (WDDM) driver for Apple AGX; Aurora's Windows desktop is "software rendered", their D3D12 work is a Mesa user-mode driver. Windows uses the Basic Display (framebuffer) path. |
| Keyboard / trackpad | m1n1 MTP + AVHD + AppleMtpInput (done in code); next run after the reinstall: `j613 mtp on` (keyboard only), driver via prep without `--no-driver`. |
